INTRO · 핵심 개념 잡기

🌟 왜 에이전트 여러 명을 팀으로 묶어야 할까요?

지금까지는 하나의 에이전트가 검색도 하고, 요약도 하고, 파일도 저장하는 '1인 만능 식당' 방식을 사용했습니다. 하지만 메뉴가 늘어나고 손님이 많아지면 요리사 한 명이 주문 접수, 재료 손질, 조리, 서빙, 회계까지 다 하다가 실수를 연발하게 됩니다.

💡 비전공자를 위한 일상 비유: "1인 동네 분식집 vs 전문 부서가 나뉜 종합 병원"

종합 병원에 가면 접수 창구(Supervisor)에서 증상을 듣고, 엑스레이는 영상의학과(Research Agent)로, 혈액 검사는 진단검사의학과(DB Agent)로, 처방전 작성은 담당 전문의(Canvas Agent)에게 차례로 연결해 줍니다.
각 에이전트에게 딱 자기 전공 분야의 프롬프트와 도구 1~3개만 전담시키면 정확도가 비약적으로 높아지고 유지보수도 훨씬 쉬워집니다!

🏃‍♂️

핸드오프 (Handoff)

이어달리기 주자가 다음 주자에게 기록지(State 업데이트)와 함께 바통(제어권 이동, goto)을 넘기는 동작입니다.

🕸️

네트워크 (Network)

별도의 팀장 없이 동료 에이전트끼리 서로의 이름을 부르며 자율적으로 공을 패스하는 수평적 협업 구조입니다.

👩‍💼

슈퍼바이저 (Supervisor)

중앙의 '팀장님' 에이전트가 모든 팀원의 업무를 배분하고, 보고를 받아 최종 답변을 정리하는 중앙 집중형 구조입니다.

📋

플래닝 (Planning)

실무에 들어가기 전 '수석 기획자'가 1~5단계 체크리스트를 먼저 세우고, 매 단계가 끝날 때마다 계획을 점검/수정합니다.

SECTION 7.2 · how_to_use_command.ipynb

7.2 핸드오프의 핵심 엔진: Command 객체 마스터하기

기존 LangGraph에서는 노드가 상태(State)만 업데이트하고, 다음 노드로 가는 길은 그래프 바깥의 add_edge나 add_conditional_edges로 따로 그려야 했습니다.
하지만 Command 객체를 사용하면 "상태 업데이트(update) + 다음 이동할 노드 지정(goto)"을 노드 함수 안에서 한 번에 처리할 수 있습니다!

💡 비유로 이해하기: "결재 서류 작성(update)과 다음 수신자 지정(goto)을 한 봉투에!"

예전에는 직원이 서류만 작성해서 책상에 올려두면, 복도 안내원이 서류를 보고 다음 부서로 날랐습니다(add_conditional_edges).
이제는 직원이 Command(update={...}, goto="agent_2")라고 서류 봉투 겉면에 "내 의견 적었으니 바로 2번 대리에게 전달해 주세요!"라고 직접 적어 보내는 것과 같습니다.

START
➔
agent_1
foo == "bar" 확인
➔
Command 분기
update + goto 동시 실행
➔
agent_2 또는 agent_3
➔
END
CHAP7_multi-agent/how_to_use_command.ipynb Command 기본 & 조건 분기 
from typing import Literal
from langgraph.types import Command
from langgraph.graph import StateGraph, MessagesState, START, END
from langchain_core.messages import AIMessage

# [ 1 ] 대화 기록(messages)에 조건 분기용 변수 'foo'를 추가한 상태 정의
class State(MessagesState):
    foo: str

# [ 2 ] 반환 타입 힌트 Command[Literal["agent_2", "agent_3"]]로 이동 가능한 후보 노드를 명시!
def agent_1(state: State) -> Command[Literal["agent_2", "agent_3"]]:
    messages = AIMessage(content="1번 에이전트 메시지입니다.")
    if state["foo"] == "bar":
        return Command(
            goto="agent_3",                                  # 3번 에이전트로 바통 터치!
            update={"messages": [messages], "foo": "baz"}  # 메시지와 foo 값을 동시에 업데이트!
        )
    return Command(
        goto="agent_2",
        update={"messages": [messages]}
    )
✅ 핵심 포인트: 왜 타입 힌트 Command[Literal[...]]를 꼭 써야 하나요?

add_edge를 생략하더라도 LangGraph가 그래프 그림(시각화)을 그리고 유효성을 검사할 때 "이 노드에서 어디로 점프할 수 있는지" 함수의 반환 타입 힌트(Literal["agent_2", "agent_3"])를 보고 파악하기 때문입니다.

SECTION 7.3 · network_agent/

7.3 네트워크(Network) 멀티 에이전트: 리서처 ↔ 차트 디자이너 자율 협업

첫 번째 실전 패턴은 네트워크(Network) 아키텍처입니다. 중앙 관리자 없이 웹 자료 조사 에이전트(researcher)와 HTML 차트 시각화 에이전트(html_generator)가 서로의 작업 결과를 보고 직접 바통을 주고받습니다.

💡 일상 비유: "취재 기자와 인포그래픽 디자이너의 복식 탁구"

1. 취재 기자(research_agent.py)가 인터넷(Tavily)에서 최신 통계 데이터를 조사합니다.
2. 만약 차트 생성이 필요 없는 단순 질문이면 "최종 답변"이라는 말을 붙여 바로 끝내고(END), 차트가 필요하면 디자이너(html_generator)에게 데이터를 넘깁니다.
3. 디자이너(chart_agent.py)는 데이터를 받아 HTML/JS 차트 파일을 생성·저장한 뒤 "최종 답변"을 외치며 업무를 종료합니다.

START
➔
🔍 researcher
TavilySearch 웹 조사
⇄
📊 html_generator
HTML/JS 차트 파일 생성
➔
END ("최종 답변" 포함 시)
CHAP7_multi-agent/network_agent/research_agent.py Gemini 3.8 Flash 기반 네트워크 노드 
def research_node(state: MessagesState) -> Command[Literal["html_generator", END]]:
    # [ 1 ] 웹 검색 에이전트 실행 (Gemini 3.8 Flash + TavilySearch)
    result = research_agent.invoke(state)

    # [ 2 ] 상대방 에이전트가 누가 보낸 메시지인지 알 수 있도록 name="researcher" 부여
    result["messages"][-1] = HumanMessage(
        content=result["messages"][-1].content, name="researcher"
    )

    # [ 3 ] '최종 답변' 키워드 유무에 따라 종료(END) 또는 디자이너(html_generator)로 이동
    last_message = result["messages"][-1]
    if "최종 답변" in last_message.content:
        goto = END
    else:
        goto = "html_generator"

    return Command(update={"messages": result["messages"]}, goto=goto)

7.4 슈퍼바이저(Supervisor) 패턴 기초: 웹 분석 + Supabase DB 관리

에이전트가 3명 이상으로 늘어나면 에이전트끼리 직접 바통을 넘기는 네트워크 방식은 동선이 너무 복잡해집니다. 이때 등장하는 해결사가 바로 중앙의 팀장님, 슈퍼바이저(Supervisor) 패턴입니다!

💡 일상 비유: "팀장님(Supervisor)과 두 명의 실무자(웹 크롤러 & DB 사서)"

실무자끼리는 직접 대화하지 않고 무조건 팀장님(supervisor)에게만 보고합니다.
• 사용자가 "이 뉴스 URL 내용을 분석해서 DB에 저장해줘"라고 요청하면:
1️⃣ 팀장님이 먼저 web_agent를 호출해 웹 본문 정제 + 확장 질문을 뽑아오게 합니다.
2️⃣ 보고를 받은 팀장님이 이어서 database_agent를 호출해 Supabase web_content 테이블에 저장시킵니다.
3️⃣ 모든 작업이 끝나면 팀장님이 직접 친절한 최종 보고서를 작성해 사용자에게 전달합니다!

CHAP7_multi-agent/supervisor_agent_web/supervisor_agent.py Router TypedDict 도구 바인딩 
class Router(TypedDict):
    """다음으로 라우팅 할 작업자"""
    next: Literal["web_agent", "database_agent"]

def supervisor_node(state: State) -> Command[Literal["web_agent", "database_agent", END]]:
    messages = [
        {"role": "system", "content": get_system_prompt(["web_agent", "database_agent"])},
    ] + state["messages"]

    # Gemini 3.8 Flash 모델에 Router 도구를 쥐여주어 다음 행동을 결정하게 함
    response = llm.bind_tools([Router]).invoke(messages)

    # [ 3 ] Router 도구를 호출했다면 -> 지목된 팀원(web_agent 또는 database_agent)에게 출동 명령!
    if hasattr(response, "tool_calls") and len(response.tool_calls) > 0:
        goto = response.tool_calls[0]["args"]["next"]
        return Command(goto=goto, update={"next": goto})

    # [ 4 ] 도구 호출 없이 바로 답변을 생성했다면 -> 모든 업무 완료! END로 이동
    else:
        final_message = AIMessage(content=response.content, name="supervisor")
        return Command(goto=END, update={"messages": [final_message]})
SECTION 7.5 · supervisor_agent_triple/

7.5 핸드오프 도구(Handoff Tools) & 병렬 Send: 3중 슈퍼바이저

7.4절에서는 슈퍼바이저가 단순히 "다음은 누구 차례!"만 지목했지만, 실무에서는 "웹 검색팀에게는 A를 조사하라고 시키고, 동시에 FAQ팀에게는 휴가 규정을 물어봐야 하는 복합 질문"이 자주 들어옵니다.
7.5절에서는 핸드오프 전용 도구(transfer_to_...)와 LangGraph의 Send API를 결합해 여러 에이전트에게 맞춤형 쿼리(query)를 동시에 병렬 배정하는 고급 기법을 구현합니다.

🌍

1. Web Search Agent

TavilySearch로 사내에 없는 외부 최신 정보나 뉴스를 검색합니다.

📚

2. DB Search Agent

Chroma 벡터 DB에 저장된 사내 PDF/Word 문서를 목록 조회하고 검색합니다.

🏢

3. FAQ Agent

사내 휴가 정책, 근무 시간, 복리후생, 부서별 연락처 4가지 전용 도구를 조회합니다.

💡 핵심 무기 2가지: ToolRuntime과 Send 병렬 호출

• 단일 부서 지시 (len(tool_calls) == 1): 일반 Command(goto=agent_name, graph=Command.PARENT)로 해당 부서 한 곳에만 이동합니다.
• 복수 부서 동시 지시 (len(tool_calls) > 1): 예를 들어 "최신 AI 트렌드도 검색해주고 우리 회사 휴가 규정도 알려줘"라고 물으면, 슈퍼바이저가 transfer_to_web_search와 transfer_to_faq 두 도구를 한꺼번에 호출합니다. 이때 Send(target_agent, {..., "query": query_content}) 리스트를 Command(goto=send_list)에 담아 두 부서가 동시에 일하게 만듭니다!

CHAP7_multi-agent/supervisor_agent_triple/handoff_tools.py 단일 Handoff vs 다중 병렬 Send 처리 
@tool(tool_name, description=description)
def handoff_to_agent(query: str, runtime: ToolRuntime) -> Command:
    state = runtime.state
    last_ai_message = cast(AIMessage, state["messages"][-1])

    # [복수 도구 호출] 2개 이상의 에이전트에게 동시에 업무를 배정할 때 -> Send 리스트로 병렬 출동!
    if len(last_ai_message.tool_calls) > 1:
        send_list = []
        for tool_call in last_ai_message.tool_calls:
            if tool_call["name"].startswith("transfer_to_"):
                target_agent = tool_call["name"].replace("transfer_to_", "")
                query_content = tool_call['args'].get('query', '')
                # 각 에이전트에게 맞춤형 query를 담아 Send 객체 생성
                send_list.append(Send(target_agent, {**state, "messages": agent_messages, "query": query_content}))
        return Command(graph=Command.PARENT, goto=send_list)

    # [단일 도구 호출] 1개 에이전트에게만 업무를 배정할 때 -> 즉시 해당 노드로 이동!
    else:
        return Command(
            goto=agent_name,
            graph=Command.PARENT,
            update={**state, "messages": handoff_messages, "query": query}
        )
SECTION 7.6 · supervisor_planning_agent/

7.6 기획(Planning) 기반 슈퍼바이저: Plan-and-Execute + 마크다운 보고서 작성

챕터 7의 대미를 장식하는 가장 정교한 아키텍처입니다. 복잡한 리서치 보고서 작성 요청이 들어왔을 때 무작정 검색부터 시작하지 않고, 수석 기획자(planning)가 전체 단계별 계획(plan)을 먼저 수립합니다.

💡 일상 비유: "수석 기획자(Planner) + 현장 매니저(Supervisor) + 리서처 & 전문 작가"

1. 수석 기획자 (planning_node): 사용자의 요청을 보고 2~5단계의 체크리스트(plan)를 만듭니다. (예: 1단계 자료조사 → 2단계 목차 및 보고서 작성/저장)
2. 현장 매니저 (supervisor_node): 전체 계획을 다 신경 쓰지 않고, 오직 현재 첫 번째 할 일(plan[0])만 딱 집어서 research 또는 canvas에게 지시합니다.
3. 실무 에이전트 (research / canvas): 리서처는 웹 조사를 수행하고, 작가(Canvas)는 목차 생성 → 마크다운 집필 → outputs/*.md 파일 저장까지 마친 뒤 매니저에게 보고합니다.
4. 계획 재검토 (Replanning): 매니저가 완료된 일을 past_steps에 적고 기획자에게 돌려보내면, 기획자가 남은 계획을 업데이트하거나 모든 목표 달성 시 최종 답변을 내고 종료(END)합니다!

# 1. planning_agent.py: 계획(Plan)과 즉시 응답(ConversationalResponse)을 Union으로 분기
class Plan(BaseModel):
    steps: List[str] = Field(description="따라야 할 단계들, 정렬된 순서여야 함")

class ConversationalResponse(BaseModel):
    response: str = Field(description="사용자의 질문에 대한 대화형 응답")

class PlanningResponse(BaseModel):
    final_output: Union[Plan, ConversationalResponse]
