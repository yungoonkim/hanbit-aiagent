1. [6.2절] 웹 검색 에이전트 만들기 (TavilySearch & 도구 호출 원리)

AI 모델(gemini-3.8-flash)은 학습된 시점 이후의 최신 뉴스나 실시간 정보를 알지 못합니다. 이 한계를 극복하기 위해 AI 전용 검색 엔진인 TavilySearch를 연결하고, 랭그래프로 [질문 판단 ➡️ 웹 검색 ➡️ 최종 답변]의 순환 고리를 직접 만들어 봅니다.

💡 일상 비유: 왜 AI가 직접 검색하지 않고 '도구 호출 주문서(tool_calls)'를 쓸까요?

많은 입문자가 "AI 모델에게 bind_tools를 하면 AI가 직접 인터넷에 접속하나요?"라고 묻습니다. 정답은 "아니요!"입니다.
• 챗봇 노드 (두뇌 / 요리사): 손님 주문을 듣고 "아, 이건 냉장고에서 '랭그래프' 재료를 꺼내와야겠군!"이라며 주문 전표(tool_calls)만 작성합니다.
• BasicToolNode (손발 / 심부름꾼): 요리사가 쓴 주문 전표를 받아 실제로 창고(인터넷)에 가서 검색 결과를 가져온 뒤, 결과 봉투(ToolMessage)에 담아 다시 요리사에게 건네줍니다!

# 1. 검색 도구 준비 및 AI 모델에 '도구 설명서' 연결하기 (bind_tools)
tool = TavilySearch(max_results=3)
llm = ChatGoogleGenerativeAI(model="gemini-3.8-flash")
llm_with_tools = llm.bind_tools([tool])

# 2. 심부름꾼 노드(BasicToolNode): AI가 작성한 tool_calls 주문서를 보고 실제 검색 실행!
for tool_call in message.tool_calls:
    tool_result = self.tools_by_name[tool_call["name"]].invoke(tool_call["args"])
    outputs.append(
        ToolMessage(
            content=json.dumps(tool_result, ensure_ascii=False),
            name=tool_call["name"],
            tool_call_id=tool_call["id"], # 어떤 주문서의 결과인지 짝을 맞춤!
        )
    )

# 3. 검색이 끝나면 다시 chatbot으로 돌아가서 검색 결과를 읽고 최종 답변을 쓰게 함!
graph_builder.add_edge("tools", "chatbot")

📊 그래프 실행 방식 5가지 완벽 비교 (invoke vs stream)

메서드 / 옵션 일상 비유 동작 방식 및 특징
invoke() / ainvoke() 📦 완제품 택배 받기 모든 노드의 작업이 끝날 때까지 기다렸다가 최종 완성된 State 전체를 한 번에 받습니다.
stream() (기본: updates) 🚚 부서별 완료 보고 문자 각 노드(chatbot, tools)가 일을 마칠 때마다 그 노드가 새로 추가한 데이터만 실시간으로 받습니다.
stream(stream_mode="values") 📸 단계별 전체 기념사진 한 노드가 끝날 때마다 지금까지 누적된 전체 메모장(State)의 스냅샷을 통째로 보여줍니다.
stream(stream_mode="messages") ⌨️ 실시간 타이핑 생중계 챗GPT 화면처럼 AI가 글자(토큰)를 생성하는 즉시 한 조각씩 실시간으로 출력합니다.

2. [6.3절] 코딩 에이전트 만들기 (@tool & create_agent)

6.2절에서는 남이 만든 검색 도구(TavilySearch)를 썼다면, 6.3절에서는 내가 직접 만든 파이썬 함수를 AI의 도구로 변신시키고(@tool), 복잡한 그래프 조립 과정을 단 한 줄(create_agent)로 줄여봅니다.

💡 핵심 포인트: 함수 안의 설명글(Docstring)은 AI가 읽는 '도구 사용 설명서'입니다!

원래 파이썬에서 """..."""(독스트링)은 동료 개발자 보라고 적는 주석이지만, @tool 데코레이터를 붙이는 순간 AI가 어떤 도구를 언제 써야 할지 판단하는 절대적인 기준표가 됩니다. 예를 들어 python_exec_tool의 설명글에 "실행 결과를 확인하고 싶다면 print(...)를 사용해야 합니다"라고 적어두면, AI가 스스로 코드 끝에 print()를 넣어서 실행합니다!

🛠️ 사용자 정의 도구(@tool)를 만드는 3가지 방법 (custom_tools.ipynb)

방식 코드 형태 언제 사용하면 좋을까요?
① 기본 @tool @tool + 타입 힌트(a: int) 입력 인자 이름만으로 의미가 명확한 아주 간단한 도구에 사용합니다.
② Pydantic 스키마 @tool(args_schema=CalculatorInput)
또는 인자에 Field(description=...)		 입력값이 복잡하거나 각 인자마다 정교한 설명과 검증 규칙을 넣고 싶을 때 사용합니다.
③ Docstring 자동 파싱 @tool(parse_docstring=True) 별도 클래스를 만들지 않고 함수 안의 Args: 주석만으로 깔끔하게 인자 설명을 등록할 때 사용합니다.
📄 coding_agent/tools.py & agent.py 오토매틱 에이전트 생성 
# [tools.py] 1. 파이썬 코드를 먼저 임포트 테스트 후 실행해보는 실험실 도구
@tool
def python_exec_tool(
    imports: str = Field(description="임포트 구문"),
    code: str = Field(description="임포트 구문을 제외한 코드 블록"),
) -> str:
    """파이썬 코드를 실행하는 도구입니다..."""
    exec(imports)                  # 1단계: 모듈 임포트 확인
    exec(imports + "\n" + code)    # 2단계: 본문 코드 실행 확인
    return f"성공적으로 코드가 실행되었습니다. :\n```python\n{code}\n```"

# [agent.py] 2. create_agent로 단 한 번에 [모델 ⇄ 도구] 순환 그래프 완성!
llm = ChatGoogleGenerativeAI(model="gemini-3.8-flash")
graph = create_agent(
    model=llm,
    tools=[python_exec_tool, file_write_tool]
)

3. [6.4절] create_agent와 미들웨어(Middleware) 완벽 마스터

create_agent는 한 줄로 에이전트를 만들어 주어 편리하지만, "AI를 부르기 전에 욕설을 차단하고 싶다면?" 혹은 "대화가 길어지면 더 똑똑한 모델로 자동 교체하고 싶다면?" 어떻게 해야 할까요? 그래프를 처음부터 다시 짜지 않고도 중간에 끼어들어 흐름을 제어하는 장치가 바로 미들웨어(Middleware)입니다.

💡 일상 비유: 건물 입구의 '보안 검색대 부스(@before_model)' vs 상담원 옆의 '귓속말 매니저(@wrap_model_call)'

미들웨어는 크게 그래프에 새로운 방(노드)을 추가하는 방식과 방 추가 없이 모델 호출만 감싸는 방식 두 가지로 나뉩니다.
• @before_model (독립 검문소 부스 추가 ⭕): 그래프 설계도에 실제로 검문소 노드가 하나 더 생깁니다. 금지어("바보" 등)가 있으면 아예 모델 방으로 가는 길을 차단합니다.
• @wrap_model_call & @dynamic_prompt (별도 부스 추가 ❌): 그래프 모양은 그대로 두고, 모델이 호출되는 순간 매니저가 개입해 모델을 교체(request.override)하거나 시스템 프롬프트(말투)를 실시간으로 바꿔줍니다.

데코레이터 그래프에 노드 추가 여부 주요 활용 사례 (실습 파일)
@wrap_model_call ❌ 추가 안 됨 (호출 감싸기) 대화 메시지 수가 10개를 넘으면 고급 모델로 동적 교체 (middleware.py)
@before_model ⭕ 노드 추가됨 (...before_model) AI 호출 전 사용자 입력에서 금지어(BLOCKED_WORDS) 필터링 및 예외 발생 (middleware_with_node.py)
@dynamic_prompt ❌ 추가 안 됨 (wrap_model_call 기반) 매 호출마다 존댓말/반말 시스템 프롬프트를 동적으로 주입 (middleware_with_node.py)
📄 create_agent/middleware.py & middleware_with_node.py 핵심 비교 3대 미들웨어 패턴 
# 패턴 1: @wrap_model_call - 대화 길이(10개 초과)에 따라 모델 바꿔치기
@wrap_model_call
def dynamic_model_selection(request: ModelRequest, handler) -> ModelResponse:
    if len(request.state["messages"]) > 10:
        return handler(request.override(model=advanced_model))
    return handler(request.override(model=basic_model))

# 패턴 2: @before_model - 그래프에 검문소 노드를 추가해 금지어 차단
@before_model
def content_filter_middleware(state: AgentState, runtime: Runtime):
    last_msg = state["messages"][-1].content
    for word in ["바보", "멍청이", "나쁜말"]:
        if word in last_msg:
            raise ValueError(f"부적절한 표현이 감지되었습니다: '{word}'")

# 패턴 3: @dynamic_prompt - 호출할 때마다 시스템 프롬프트(말투) 동적 변경
@dynamic_prompt
def random_tone_prompt(request: ModelRequest) -> str:
    return "항상 존댓말로 정중하게 답변하세요."

4. [6.5절] 스스로 검증하고 교정하는 Self-RAG 에이전트 만들기

일반적인 RAG(검색증강생성)는 문서를 검색해 오면 무조건 그걸 보고 답을 씁니다. 하지만 ① 검색된 문서가 질문과 전혀 상관없는 내용일 때나, ② AI가 문서에 없는 내용을 지어내어 거짓말(환각, Hallucination)을 할 때가 문제입니다. 6.5절에서는 2명의 AI 심사관(Grader)을 배치해 스스로 질문을 고쳐 재검색하고 환각을 잡아내는 완성형 RAG 에이전트를 구현합니다.

📚 일상 비유: 국립국어원 도서관의 '5개 전문 부서'와 '2명의 깐깐한 심사관'

우리가 만든 rag_agent는 264페이지 분량의 『한글 맞춤법·표준어 규정 해설』 PDF가 510개의 조각(청크)으로 저장된 디지털 도서관(Chroma DB)을 사용합니다.
• 1차 심사관 (decide_to_generate): 사서가 가져온 문서가 질문과 관련 있는지 yes / no로 채점합니다. no라면 질문 교정 전문가(transform_query)에게 보내 질문을 더 똑똑하게 바꿔서 다시 검색하게 합니다! (최대 3회)
• 2차 심사관 (check_hallucinations): 집필가(generate)가 쓴 답변이 문서의 사실(팩트)에 근거했는지 yes / no로 채점합니다. 근거 없는 거짓말(not supported)이라면 다시 답변을 쓰게 돌려보냅니다!

🧩 자주 묻는 질문: rag_agent/state.py에서 리듀서(Reducer)는 어디에 쓰였나요?

"리듀서(Reducer)라는 게 채팅 대화를 계속 누적시키려고 쓰는 건가요?" ➡️ 네, 맞습니다! 랭그래프의 상태(State)는 기본적으로 새 값이 들어오면 기존 값을 덮어쓰기(Overwrite)합니다. 따라서 지워지지 않고 카카오톡 대화창처럼 차곡차곡 쌓아야 하는 칸에는 반드시 리듀서(합치기 규칙)를 붙여주어야 합니다.

rag_agent/state.py의 GraphState를 보면, 리듀서를 쓰는 변수와 리듀서를 안 쓰는 변수가 왜 나뉘어 있는지 한눈에 이해할 수 있습니다:

GraphState 변수 코드 정의 방식 리듀서 사용 여부 이렇게 설계한 이유 (비유)
messages
(MessagesState에서 상속)		 Annotated[list, add_messages] ⭕ 리듀서 O (대화 누적) 카카오톡 대화창처럼 이전 질문과 AI 답변을 지우지 않고 아래에 계속 이어 붙여야 대화 맥락이 유지됩니다.
question question: str ❌ 리듀서 X (덮어쓰기) 질문 교정 전문가(transform_query)가 질문을 다듬으면, 이전의 어색한 질문은 지우고 가장 최신 질문 1개로 갈아끼워야 합니다.
documents documents: List[Document] ❌ 리듀서 X (덮어쓰기) 재검색을 했을 때 이전에 잘못 찾았던 엉뚱한 문서들은 지우고, 새로 찾은 문서들로 교체해야 합니다.
retry_num retry_num: int ❌ 리듀서 X (덮어쓰기) 현재 몇 번째 재시도인지(1 ➡️ 2 ➡️ 3) 최신 숫자 1개만 기록하면 됩니다.

# AI가 사설 없이 오직 'yes' 또는 'no'로만 딱 떨어지게 채점하도록 Pydantic 스키마 정의
class Grade(BaseModel):
    binary_score: str = Field(description="문서가 질문과 관련이 있는지 여부, 'yes' 또는 'no'")

# with_structured_output(Grade)를 붙이면 무조건 Grade 객체 형태로만 응답을 반환합니다!
grader = llm.with_structured_output(Grade)
score = (grader_prompt | grader).invoke({"question": question, "context": context})

if score.binary_score == "no":
    return "transform_query"  # 관련 없으면 질문을 다듬어서 재검색!
else:
    return "generate"         # 관련 있으면 답변 작성으로 이동!
⚠️ 무한 루프 방지 장치 (retry_num >= 3)

만약 사용자가 한글 맞춤법 PDF에 전혀 없는 질문(예: "오늘 서울 날씨 어때?")을 했는데도 계속 질문을 바꿔가며 영원히 재검색하면 큰일 나겠죠? 그래서 transform_query를 거칠 때마다 retry_num을 1씩 올리고, 3번 이상 실패하면 재검색을 멈추고 현재 문서 안에서 답할 수 있는 대체 질문들을 친절히 추천하도록 설계되어 있습니다.
