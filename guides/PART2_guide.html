1. 상태 (State)

"공유 업무 메모장"
AI 작업자들이 돌려보면서 질문과 답변을 적어두는 공용 바구니(딕셔너리)입니다.

🧑‍🍳

2. 노드 (Node)

"작업자 (담당 부서)"
메모장을 받아서 실제로 일(번역, 요약, 검문 등)을 처리하는 파이썬 함수입니다.

➡️

3. 엣지 (Edge)

"복도 화살표 (이동 경로)"
A 작업자가 일을 마치면 다음엔 B 작업자에게 가라고 알려주는 길입니다.

➕

4. 리듀서 (Reducer)

"메모장 정리 규칙"
새 메모가 들어왔을 때 기존 내용을 지우고 덮어쓸지, 아래에 이어붙일지 정하는 규칙입니다.

1. 첫 번째 AI 모델(LLM) 호출하기

랭그래프를 본격적으로 배우기 전에, 파이썬 코드로 Google의 gemini-3.5-flash-lite 모델에게 역할을 부여하고 대화를 나누는 가장 기본적인 방법입니다.

💡 일상 비유로 이해하기: 영화 촬영장

AI에게 말을 걸 때는 두 가지 메시지가 필요합니다.
• System 메시지 = 감독님이 배우(AI)에게 주는 "너는 지금부터 유능한 영어 번역가야!"라는 배역 설정서입니다.
• Human 메시지 = 실제 관객(사용자)이 배우에게 건네는 "안녕하세요."라는 대사입니다.

📄 PART2/4.4_main.py Python 기초 
# 1. 필요한 도구 가져오기
from langchain_google_genai import ChatGoogleGenerativeAI
from dotenv import load_dotenv

# 2. .env 파일에서 비밀 출입증(GOOGLE_API_KEY) 불러오기
load_dotenv()

# 3. gemini-3.5-flash-lite 인공지능 모델 준비하기
llm = ChatGoogleGenerativeAI(model="gemini-3.5-flash-lite")

# 4. AI에게 전달할 대본(메시지 리스트) 작성하기
messages = [
    ("system", "당신은 사용자가 한 말을 영어로 번역하는 유능한 번역가입니다."),
    ("human", "안녕하세요."),
]

# 5. AI 실행하기 (invoke = '작동시키다')
ai_msg = llm.invoke(messages)
print(ai_msg)
✅ 핵심 문법 포인트
  • load_dotenv(): 내 컴퓨터의 .env 파일에 적어둔 API 키를 안전하게 불러옵니다. 코드에 비밀번호를 직접 적지 않기 위해 사용합니다.
  • llm.invoke(messages): invoke는 랭체인과 랭그래프에서 "자, 이제 실행해!"라고 명령할 때 가장 많이 쓰는 마법의 단어입니다.

2. 그래프의 상태(State) 정의하기: TypedDict vs Pydantic

랭그래프에서 여러 단계(노드)를 거치며 일을 처리하려면, 데이터를 담아 전달할 공유 메모장(State)의 양식을 먼저 정해야 합니다. 파이썬에서는 주로 TypedDict와 Pydantic(BaseModel) 두 가지를 사용합니다.

💡 일상 비유: 종이 설문지(TypedDict) vs 인터넷 회원가입 창(Pydantic)

• TypedDict (종이 설문지): 칸에 "이름(문자)"이라고 적혀 있어서 작성자에게 안내해 주지만, 누군가 이름 칸에 숫자 123을 적어도 종이가 찢어지거나 막지는 않습니다. (가볍고 빠름)
• Pydantic BaseModel (인터넷 회원가입 창): 이름 칸에 숫자 123을 적고 '제출'을 누르면 즉시 "삐빅! 문자열만 입력하세요(ValidationError)"라며 빨간 경고창을 띄웁니다. (엄격하고 안전함)

구분 TypedDict Pydantic (BaseModel)
역할 데이터 구조(키와 자료형)를 알려주는 가벼운 안내판 실제 데이터가 규칙에 맞는지 실행 중에 엄격히 검사하는 보안관
잘못된 타입 입력 시 에러 없이 그대로 통과됨 ('name': 123 허용) 즉시 ValidationError 발생시켜 실수 차단
랭그래프 활용 속도가 빠르고 간단해서 기본 상태(State) 정의에 가장 많이 사용 입출력 데이터 검증이 꼭 필요한 중요한 에이전트에 사용

3. 상태에 리듀서(Reducer) 함수 추가하기: "왜 대화를 누적하려면 리듀서가 필요할까요?"

랭그래프를 처음 배울 때 가장 많이 궁금해하시는 질문이 바로 "리듀서(Reducer)라는 게 채팅 대화를 계속 누적시키려고 쓰는 건가요?"입니다. 네, 정확히 맞습니다!

랭그래프의 상태(State, 공유 메모장)는 아무 설정을 하지 않으면 새로 들어온 값으로 기존 값을 덮어쓰기(Overwrite, 기존 내용 삭제)합니다. 따라서 카카오톡 대화창처럼 이전 질문과 AI의 답변을 지우지 않고 차곡차곡 쌓아두려면 반드시 리듀서(Reducer)를 지정해야 합니다.

💡 한눈에 비교하기: 리듀서가 없을 때(화이트보드 지우기) vs 리듀서가 있을 때(공책에 이어 적기)

• ❌ 리듀서가 없을 때 (messages: list) — "화이트보드 지우고 새로 쓰기"
  1) 사용자가 "안녕! 내 이름은 박철수야"라고 말함 ➡️ messages = ["안녕! 내 이름은 박철수야"]
  2) AI 노드가 "반가워요 철수님!"이라고 답함 ➡️ 기존 질문을 지워버리고 messages = ["반가워요 철수님!"]만 남음!
  3) 다음 턴에 "내 이름이 뭐라고 했지?"라고 물으면 이전 대화가 사라져서 기억하지 못합니다.

• ✅ 리듀서가 있을 때 (messages: Annotated[list, add_messages]) — "카카오톡 대화창처럼 아래에 이어 붙이기"
  1) 사용자가 "안녕! 내 이름은 박철수야"라고 말함
  2) AI 노드가 "반가워요 철수님!"을 반환하면, 리듀서(add_messages)가 작동해 기존 목록 뒤에 새 대화를 이어 붙입니다.
  3) 결과: messages = ["안녕! 내 이름은 박철수야", "반가워요 철수님!"] (대화 맥락 완벽 유지!)

📊 리듀서(Reducer)의 진짜 의미: "기존 값 + 새 값 합치기 규칙"

즉, 리듀서의 본래 의미는 "노드가 새로운 결과값을 내놓았을 때, 기존 메모장(State)에 있던 값과 어떻게 합칠지 정해주는 규칙(함수)"입니다. 그래서 변수의 성격에 따라 리듀서를 쓰기도 하고 안 쓰기도 합니다.

상태(State) 변수 예시 코드 작성 방식 동작 방식 일상 비유
채팅 대화 내역 messages: Annotated[list, add_messages] 리듀서 O (누적) 카카오톡 대화창처럼 이전 대화 아래에 새 말을 계속 쌓음
수집한 자료 목록 items: Annotated[list, operator.add] 리듀서 O (누적) 여러 에이전트가 찾아온 검색 결과를 하나의 바구니에 합침
재시도 횟수 / 최신 질문 retry_count: int
question: str		 리듀서 X (덮어쓰기) 이전 값은 필요 없고 가장 최신 값 1개로만 갈아끼움
📄 리듀서(Reducer)와 add_messages 비교 핵심 개념 
from typing import TypedDict, Annotated
from langchain_core.messages import AnyMessage
from langgraph.graph.message import add_messages

# [방법 1] 직접 더하기(+) 함수를 만들어 리듀서로 지정하기
def add(left, right):
    return left + right  # 기존 리스트(left) 뒤에 새 리스트(right)를 이어붙임

# [방법 2] 랭그래프 표준 방식: 똑똑한 add_messages 리듀서 사용하기
class State(TypedDict):
    messages: Annotated[list[AnyMessage], add_messages]
🌟 왜 단순 더하기(add) 대신 add_messages를 쓸까요?

1. 새로운 ID의 메시지가 들어오면 → 기존 대화 목록 맨 뒤에 추가(Append)합니다.
2. 이미 있는 ID와 똑같은 ID의 메시지가 들어오면 → 중복해서 쌓지 않고 기존 메시지를 새 내용으로 똑똑하게 수정(Update)해 줍니다!

4. 노드(Node), 일반 엣지(Edge), 조건부 엣지(Conditional Edge)

상태(메모장)를 만들었다면, 이제 일할 사람(노드)을 뽑고 이동 동선(엣지)을 그려줄 차례입니다.

① 노드(Node) 추가하기 = 작업자 배치

노드는 현재 state를 입력받아 작업을 수행한 뒤, 변경할 내용을 딕셔너리로 반환하는 일반 파이썬 함수입니다.

② 일반 엣지 vs 조건부 엣지 = 외길 vs 갈림길

START (출발)
➡️
chatbot 노드
➡️
❓ 글자 수 > 1000자?
➡️
True: summary (요약) / False: END (종료)
📄 조건부 엣지(갈림길) 만드는 코드 패턴 5.2.5절 
# 1. 갈림길 안내원(라우팅 함수): 상태를 보고 어디로 갈지 판단합니다.
def routing_function(state: State):
    if len(state["messages"][-1]) > 1000:
        return True   # 1000자가 넘으면 True
    return False      # 1000자 이하이면 False

# 2. 조건부 화살표 연결: (출발노드, 판단함수, {판단결과: 도착노드})
graph.add_conditional_edges(
    "chatbot",
    routing_function,
    {True: "summary", False: END}
)

5. [실습 1] 입·출력 양식이 분리된 기본 챗봇 그래프

실제 서비스를 만들 때는 사용자가 넣는 입력(InputState), 내부에서 복잡하게 돌아가는 전체 메모(OverallState), 그리고 사용자에게 깔끔하게 보여줄 최종 결과(OutputState)를 분리하면 훨씬 깔끔합니다.

🍽️ 식당 비유로 이해하는 3가지 State

• InputState (손님용 주문서): 손님은 복잡하게 알 필요 없이 question(주문 메뉴)만 적어서 냅니다.
• OverallState (주방 내부 현황판): 주방 안에서는 주문 내역, 조리 기록(messages), 완성 요리 등을 모두 기록하며 관리합니다.
• OutputState (손님용 배식 쟁반): 손님 식탁에는 주방의 복잡한 메모를 빼고 깔끔하게 완성된 answer(답변 요리)만 내어갑니다!

📄 5.3.1절 전체 흐름 요약 그래프 컴파일 & 실행 
# 입구(input_schema)와 출구(output_schema)를 분리하여 그래프 설계도 생성
graph_builder = StateGraph(
    OverallState,
    input_schema=InputState,
    output_schema=OutputState
)

# 노드 등록 및 화살표 연결 후 compile()로 실행 가능한 프로그램 완성!
graph_builder.add_node("chatbot", chatbot)
graph_builder.add_edge(START, "chatbot")
graph_builder.add_edge("chatbot", END)
graph = graph_builder.compile()

# 실행 결과: OverallState의 messages는 숨겨지고 OutputState의 answer만 깔끔히 출력됨!
graph.invoke({"question": "대한민국의 수도는 어디인가요?"})
# 👉 출력: {'answer': '대한민국의 수도는 서울특별시입니다.'}
